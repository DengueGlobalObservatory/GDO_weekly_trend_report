## Step 1 — fetch (where it failed, and why this is a *different* gap)

**Sub-part that is now resolved:** the earlier run today (`BLOCKED` commit
`30e9b68`) found `api.github.com/repos/.../contents/Output` returning 403
with "GitHub access is not enabled for this session... An org admin must
connect the Claude GitHub App." Re-tested this run: after `add_repo`-ing
`DengueGlobalObservatory/DENV_global_observatory` with `access: push`, the
same Contents API endpoint now returns `200` and lists `Output/2026_08_04/`
correctly, including `DENV_cases_nowcast_output.csv`. **Treat this gap as
resolved** — an org admin must have connected the Claude GitHub App for
`DengueGlobalObservatory` since the 2026-08-12 morning run.

**New failure, this run:** `Rscript R/run_weekly_pipeline.R` got past the
Contents API listing this time, but failed in `fetch_snapshot()` →
`download_raw_csv()`:

```
Error in download_raw_csv(folder_name, raw_csv_path) :
  download_raw_csv(): failed to download https://raw.githubusercontent.com/DengueGlobalObservatory/DENV_global_observatory/main/Output/2026_08_04/DENV_cases_nowcast_output.csv (status 404)
```

Diagnosis (isolated with direct `curl`, bypassing R entirely):

- `curl` to the exact same URL **with no auth header** → `HTTP 200`, correct
  CSV body (confirmed by re-fetching and inspecting the first bytes).
- The identical `curl` with `-H "Authorization: token $GITHUB_TOKEN"` (the
  same header `R/fetch_snapshot.R`'s `gh_headers()` attaches whenever
  `Sys.getenv("GITHUB_TOKEN")` is non-empty, which it is in this session) →
  `HTTP 404`, body literally `404: Not Found`.

So the file is public and fetchable — the problem is that `gh_headers()`
attaches this session's `GITHUB_TOKEN` (needed for `api.github.com` calls,
per the resolved gap above) to **every** `httr::GET()` call in
`fetch_snapshot.R`, including the `raw.githubusercontent.com` download that
neither needs nor wants it. In this sandbox, sending that
session-scoped/proxy token to `raw.githubusercontent.com` makes GitHub (or
the egress proxy in front of it) return 404 instead of just ignoring an
unrecognised-scope token. `get_path_commit_sha()` (the Commits API call)
would presumably need the token and work fine — this run never reached it
because `download_raw_csv()` errors first.

## What's needed to unblock

This is a code-level fix, not a permissions gap — but per the same
principle the 2026-08-11/08-12 runs have already applied ("a change to the
deterministic pipeline script... is left for a human to decide on, not
made unilaterally by this routine"), no edit was made unilaterally.
Suggested fix for a human to review: in `R/fetch_snapshot.R`, only attach
the `Authorization` header for `api.github.com` calls
(`list_output_folder_dates()`, `get_path_commit_sha()`), not for the
`raw.githubusercontent.com` download in `download_raw_csv()` — e.g. give
`download_raw_csv()` its own headers helper that only sets `User-Agent`,
or make `gh_headers()` take a `use_auth = TRUE` argument.
